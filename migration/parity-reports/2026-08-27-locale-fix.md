# Language switching does not change UI language — Agent L manual-QA bug fix pass 2026-08-27

Scope: BUG 5 (diagnosed) — changing language in Settings did not change any UI language; React authority `packages/client/locale/src/client/*` (`index.ts` LocaleRuntime, `LanguageRow.tsx`, `settings-store.ts`, `../locale-settings.ts`); no row promoted past Integrated; Gatekeeper not run.

Root cause confirmed: `LanguageRowController.setLocale` (`apps/flutter/lib/src/features/settings_general/widgets/language_row.dart`) wrote only `settings.mutate(ns 'locale')` and its own provider state — it never called the activated `LocaleService.setLocale`, so the runtime snapshot every dictionary consumer reads through `bind()` stayed on its default `'zh'` and no mounted `_t()` text could change; additionally nothing connected `MaterialApp`'s `locale:` to the service, so `Localizations.localeOf` consumers (`plugins/conversation/ui/chat_view.dart` compaction card ~lines 290/321/383) had no language to follow.

React contract cited: `LanguageRowInjected.setLocale` → `locale.setLocale(id)` publishes the snapshot first and only then performs the durable write (`void this.host?.set(LOCALE_PREFERENCE_FIELD, match.id)`) — persistence is a consequence, not the switch mechanism (`packages/client/locale/src/client/index.ts` setLocale, lines ~212–217); boot restores the preference via constructor scope adoption (`adopt(host)` + `host.subscribe`), all subscribed renderers rebuild through the snapshot revision, and `<html lang>` follows every switch.

Fix — publish path: `setLocale` now calls the shared activated service (`ref.read(localeServiceProvider)`, provided by `CoreServicesPlugin` as the `'locale'` service so bootstrap, the row, and plugin consumers see ONE instance) BEFORE the guarded `settings.mutate`, and on failure rolls back BOTH sides — republishes the previous id on the service and restores the row's optimistic active/revision (mirroring publish-then-persist with rollback).

Fix — app-layer rebuild: `_buildRoot` in `core/bootstrap/app_plugins.dart` binds `MaterialApp.router`'s `locale:` to the new `materialLocaleProvider` (maps the active id onto `Locale('zh')`/`Locale('en')`) fed by the new `localeRevisionProvider` (the uSES subscribe/getSnapshot analog over `LocaleService.onChanged`), plus `supportedLocales: [zh, en]` and Flutter's global localization delegates (SDK `flutter_localizations`, already a dependency) so Material's own strings follow the switch without introducing a second localization framework — product copy stays on LocaleService dictionaries.

Fix — boot adoption/persistence: new `features/locale/locale_preference.dart` extracts the durable `locale` section parse (namespace `'locale'`, field `'preference'`, mirrors `locale-settings.ts`) and `adoptPersistedLocale(client, service)` applies the persisted preference at activation from `CoreServicesPlugin.apply`; a stale id outside the registry or an unreachable describe leaves the default standing, matching React's adopt-without-validation.

Fix — bind consumer rebuild wiring: verified by grep that the compaction card is driven purely by `Localizations.localeOf` (rebuilt automatically by the MaterialApp binding; file untouched per ownership), while the directory browser's injected `t` is the stable bind function invoked at call time whose widget never rebuilt — `BrowseDirectoryFlow` now watches `localeRevisionProvider` so Miller-dialog copy re-renders on every publish; remaining plugin UI files hardcode `kXxxEn[...]` maps at render time and never read the service (pre-existing gap out of BUG 5's scope, noted below).

Tests added: extended `test/features/settings_general/language_row_test.dart` (+4: publish-through-service-before-persist with journal ordering and captured ns/ops/expectedRevision, rollback of BOTH controller state and service on mutate conflict with exactly two publications, unknown id surfaces `ArgumentError` text before any wire traffic and keeps the previous locale, existing 7 cases unchanged green); new `test/features/locale/locale_binding_test.dart` (5: materialLocaleProvider zh→Locale('zh') mapping following switches, one `setLocale('en')` flips BOTH a bound string and a `Localizations.localeOf` probe without restart, failed durable write republishes the previous language in both channels, restart simulation where fresh container+service seeded `preference:'en'` boots English via `adoptPersistedLocale`, fallback-to-key already covered by `runtime_services_test.dart` line "missing.key"); new `test/features/locale/locale_bootstrap_test.dart` (1: `CoreServicesPlugin` boots via real `PluginHost` and adopts the persisted preference into the activated shared service instance).

Verification: `flutter analyze lib` 0 errors and zero findings in touched files (remaining warnings/infos pre-existing elsewhere); `flutter test test/features/locale test/features/settings_general/language_row_test.dart test/services/runtime_services_test.dart test/plugins/directory_picker` 53/53; `flutter test test/integration/hub_integration_test.dart` passes proving full-host activation still boots with the new bootstrap wiring; `pnpm run verify-flutter-tracker --check` OK (112 items) after tracker deltas; `test/widget_test.dart` and `test/integration/business_host_test.dart` currently fail to compile/run against another agent's mid-flight `conversation/ui` composer/router/HoleRenderer refactor (undefined `welcomeModelCatalogProvider`, `entry.component is HoleRenderer` assertions) — unrelated surfaces, not exercised or modified here.
