# Parity report — approval plane, pending-interaction reconciliation, tool-call-delta streaming, host-born session policy (2026-08-26)

This report covers four core/runtime rows advanced from Audited to Integrated in the same wave: runtime.pending-interactions, interaction.plane, state.streaming-tool, and runtime.host-born-sessions.

runtime.pending-interactions is now complete end-to-end in the Flutter client. The question half (store keyed by envelope rpcId, batch answering through ConnectionClient.respond, resolution matched by rpcId) already shipped; this wave added the missing approval half and the shared reconciliation: ApprovalsController stores PendingApproval waits keyed by session with idempotent replay replacement and approvalId-matched settlement (port of packages/client/runtime/src/client/sessions/session.ts mint/settle over approval/requested + approval/resolved), ApprovalResponder posts the client-response echoing the requested frame's rpcId with {sessionId, approvalId, outcome} where outcome accepts only allowed-once | rejected (packages/host/apiproxy/src/api/approvals.ts ApprovalResponsePayload), and live_sync.dart routes both approval frame types plus both question types into the stores and then recomputes SessionSummary.pendingInteraction.

The sidebar reconciliation mirrors the React list fold exactly: stable wait keys a:<approvalId> and q:<rpcId>, plan-review narrowing via planReviewOf (same predicate as manager.ts questionInteractionStatus), question outranks approval when both wait (manager.ts buildListSnapshot precedence), resolution of one wait keeps the dot with the surviving sibling kind, and host/session-removed drops that session's waits entirely.

Reconnect behavior matches React's generation-drop rule: installPendingInteractionResync listens on connectionStateProvider and, entering reconnecting or disconnected, clears every live wait and summary marker; mux-open replay re-adds still-pending requests with their live rpcIds, which the store replacement semantics accept idempotently.

interaction.plane now has its full collaboration surface. The approval card (ui/approval_card.dart) ports ui-conversation's ApprovalPanel: amber waiting strip, reason headline falling back to "Escalation: <toolName>", reject/allow-once actions with a one-shot latch that re-arms on a failed answer, and frame-driven removal when the resolved broadcast settles the store. It registers as a composer-chain takeover at priority 1 so a pending question (default priority 0) wins the chain when both kinds wait, mirroring ui-conversation apply.ts registration order. React additionally renders the paired tool call's command line by reading running-call argsRaw; the Flutter node fold does not retain argument text, so that line is honestly absent rather than invented.

state.streaming-tool traced to truth: there is no dedicated tool-call-delta wire frame anywhere. The durable contract is the assistant/chunk session event carrying {turn, step, chunk: StreamChunk} (packages/core/session/src/types.ts), appended per delta by the agent loop (packages/core/agent-loop/src/agent.ts), and React accumulates tool arguments inside PartialAccumulator.push case 'tool-call-delta' (packages/client/runtime/src/client/sessions/partial.ts lines 67-78): first non-empty callId wins, latest name wins, argumentsDelta fragments concatenate verbatim. The Flutter client previously read only chunk.text, dropping argument partials. The new core/events/tool_stream.dart decodes the chunk union and accumulates partial tool calls per step, and ConversationNodeFolder routes assistant/chunk deltas through it — argument fragments now surface on the in-flight AssistantNode as partialToolCalls and clear when the step's message settles; text and reasoning chunks keep their previous append behavior byte-for-byte. The committed parity fixtures carry zero tool-call-delta frames (apps/flutter/test/goldens/replay/parity-stream.jsonl), so the semantic-parity byte comparison is unaffected and stays green.

runtime.host-born-sessions resolved its carrier collision by extraction instead of a second claim: core/session/host_session_policy.dart now owns the creation policy as pure functions — sessionCreatePayload builds the session.create wire body, isWorkspaceAttachFailure classifies the single sanctioned retry (workspace-not-found transport literal), and adoptHostBornSession projects the blank, idle summary at adoption time (manager.ts create arm: a created session is blank by definition). All three creation carriers consume it without changing their flow: ConnectionClient.createSession builds its payload through the policy, and sidebar._handleNewSession, sidebar onCreateIn, and app_router._handleSubmit classify attach failures through it while adopting exactly the host-returned id; the two sidebar/welcome flows additionally project the adopted blank summary before the confirming list pull lands, matching React's synchronous-addressability guarantee.

Evidence: flutter analyze lib reports zero errors; the new suites (test/plugins/ws_input/approval_plane_test.dart 15 tests covering store semantics, wire payload, plane dispatch, unknown-frame discard, card widget behavior, and reconciliation/resync; test/session/tool_stream_test.dart 7 tests using real chunk shapes from the llm assembler and agent-loop mock fixtures; test/session/host_session_policy_test.dart 5 tests) pass, and the affected neighboring suites stay green (ws_input group, unit/live_sync_test, unit/sessions_controller_test, api/connection_client_rpc_test, conversation nodes/plugin tests, replay pair including the semantic-parity byte compare, integration/business_host_test).
